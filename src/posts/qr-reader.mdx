QR codes are everywhere around us. They have been around since the 90s. Detecting and decoding them should be a simple, straightforward computer vision task, right? At least that's what I thought. I set out to write my own QR code detector, trying to come up with an algorithm myself. Turns out it's not as simple as I thought.

The scope of my project is simple: detect a QR code, find its corners, and decode the payload. Before we do that, let's look at a QR code:

// insert image of qr code

You may notice the patterns at the top left, top right and bottom left corners. These are the _finder patterns_ of a QR code. They are always there, and do not contain any data themselves. They are purely there to aid in detecting the QR code. If you pass a horizontal or vertical line through these patterns, then you always see black, white, black, white, black in a ratio of 1:1:3:1:1. This pattern makes it relatively easy to find these finder patterns, and we'll talk more later on how you can do that.

To detect a QR code you just need to find 3 things roughly in an isosceles triangle that look like a finder pattern using the 1:1:3:1:1 rule. In this triangle we have one right angle and two 45 degree angles, and we know the finder pattern at the right angle must be the top left. If we assume the QR code isn't mirrored, we then know the bottom left follows counter clockwise after the top left finder pattern, and the top right sits clockwise after the top left corner.

There's more though. QR codes can have different sizes, known as _versions_. The smallest QR codes are version 1 and are 21x21 dots, up to version 40 which is 177x177. In general version $V$ has $17+4V$ dots on each side. To decode it, you definitely need to know what the version is. Fortunately, we know that the finder pattern is 1+1+3+1+1=7 dots on each side, so if we e.g. know that the finder patterns are 70px on each side and there is 110px between each finder pattern, then we know one dot is 10px, and we have 70+110+70 = 25 dots on each side in total, so it must be version 2. This works very well for small versions, but for big versions we may only be able to estimate the version to be in the range 32-35. In that case, we could just try to decode it assuming it was one of those versions, and try the next version if things don't work out. Part of the QR code payload is also the version number so that helps.

// Show a diagram with versions and how we can estimate them

To actually decode it now, we do need to know with some precision where the corners of the 3 finder patterns are. This way we can establish a correspondence from pixels to the dot pattern. For example, if we want to know if the dot at (4,10) is black or white, we know which pixels to look at in the original image. The more precisely we know the location and orienation of the finder pattern, the better this correspondence will, and the more likely we will be able to successfully decode the QR code.

This suggests the following pipeline:

- Find parts of the image that look like finder patterns using the 1:1:3:1:1 rule.
- Find the corners of the finder patterns, or reject the candidates that fail
- Find which triplets of finder patterns actually make up a QR code
- Determine the version `V`, and thus the number of dots `N=4*V+17` on each side.
- Sample the QR code to get the `NxN` dot pattern
- Decode the payload

This is at a high level the pipeline I implemented. One thing we're leaving out are the _alignment patterns_. These are smaller 1:1:1:1:1 patterns (black outer ring, inner white ring, black dot in center) you can see in all QR codes with version >1. Their locations and number depend on the version of the QR code. Since the sampling step requires knowing the QR code geometry more precisely at higher versions, these help to improve the localization of the QR code. For the sake of simplicity I decided to leave these out of my algorithms, since they aren't strictly necessary to successfully decode a QR code, even at higher versions, as we will see.

Then finally, there is the matter of _perspective_. If you capture a QR code dead on, then it's much easier to decode. I want my detector to be able to handle QR codes that are rotated or viewed at weird angles. Basically, if you snap an image of a QR code from any odd angle, I want the detector to be able to find it. This is much more satisfactory than requring the code to already be basically aligned in the first place. But as we will see, it also makes the problem much harder.

I hope the basic ideas and scope of this project are now clear, so let's dive right in to how the steps in this algorithm work.
